# Architecture

A FastAPI server on 127.0.0.1 serves static pages and a JSON API. There is **no build step**: the
browser loads ES modules from `web/` as they are. Files are the database for the DAW; the
generator uses SQLite.

## Backend (`tunelab/`)
| File | Role |
|---|---|
| `server.py` | Assembles the app: pages, routers, error mapping, host check |
| `routes_daw.py` | API: library, settings, notation conversion, scoring, WAV to MP3 (ffmpeg) |
| `routes_generator.py` | API: generate, list, score typed notation |
| `routes_transcriber.py` | API: record, analyse, result; holds the one current recording |
| `documents.py` | **DAW file formats** (pydantic) and conversion to and from `notation.Tune` |
| `library.py` | File storage: atomic writes, ids, revisions, favorites, trash, settings, kept recordings |
| `notation.py` | Text notation and the `Tune` object used by generator, scorer, extractor |
| `generator.py`, `scorer.py`, `pipeline.py`, `check.py` | Generate, score, flag, test the scorer |
| `extract.py`, `synth.py` | Audio to melody; offline synth for tests |
| `capture.py` | Records one browser's output stream through `parec` |
| `transcribe.py` | Recording to melody candidates; runs as its own process |
| `guide.py` | Melody inside areas the user highlighted; pictures and sounds for that; its own process |
| `models.py` | Optional neural networks: vocal separation, sung pitch, beats |
| `melody_check.py` | Tests the transcriber on hand-corrected clips |
| `db.py` | SQLite of generated tunes (`data/tunes.db`) |

synths), **@tonejs/midi**, **tinykeys**. All MIT; licenses sit in `web/vendor/`.

## Core concepts

**Two time units.** `notation.py` uses 12 ticks per beat; the DAW uses `PPQ = 480`. One notation
tick is 40 DAW ticks (`documents.SCALE`). The DAW is finer so that scaled groups and imported MIDI
keep their shape. Converting DAW to notation can round, and fails on overlaps. A beat is always a
quarter note. `PPQ`, `MAX_TICK` and the allowed sounds, modes and meters are defined in both
`documents.py` and `model.js` and must agree.

**Immutable projects.** Operations in `model.js` return new objects, and return the *same* array
when nothing changed. Undo is a list of earlier project objects; "unsaved" means
`state.project !== state.saved`. Never modify a note, track or project in place.

**Ids.** Note and track `id`s exist only in the session and are stripped when saving.

**Data flow.** Input -> `store.commit(...)` -> every subscriber re-reads the state. `store.set`
changes view state (tool, grid) without an undo step.

**Gestures.** `roll.js` runs one gesture at a time, previewing by moving Konva shapes. Only `end()`
commits, so a drag is one undo step. Any store change redraws, which cancels a running gesture.
Shortcuts other than Escape are ignored during a drag.

**Group scaling.** Konva's Transformer supplies the handles; `boundBoxFunc` turns the dragged edge
into one factor, limited by `limitFactor`; `scaleNotes` applies it. Starts and ends are rounded,
never lengths, so touching notes stay touching.

**Roll coordinates.** The stage is only as large as the visible area and stays put (sticky) while a
large empty div scrolls. Layers are shifted by the scroll offset. `ox()`/`oy()` give time 0 and
pitch 127.

**Playback.** The transport counts in DAW ticks. Note or tempo changes while playing reschedule
everything. `active` is our own flag because the transport starts slightly in the future.

**Audio export.** `render` in `player.js` plays the tracks through the same synths in `Tone.Offline`,
so the file sounds like Play; `audibleTracks` (mute and solo) is shared with playback. The browser
encodes WAV; MP3 goes through `/api/audio/mp3`, where ffmpeg writes to a temporary file, because
through a pipe it cannot write the header that tells players the duration.

**Click latency.** A preview sounds inside the click handler, before any redraw (`press` in
`roll.js`), at `Tone.immediate()`. `Tone.now()` would add the 0.1 s look-ahead. Keep the look-ahead
itself: at 0.05 s notes came late when editing a dense project during playback.

**Keyboard notes.** While on, `piano.js` takes its keys in the capture phase and stops the event, so
the shortcuts on the same keys never see it. Every press has an id (which key or mouse button) and
is released by that id, on the track and pitch it started with. Keys are released when the window
loses focus, or they would sound forever.

**Panels update in place** rather than being rebuilt, so that redraws never steal focus from a
field being typed in. `setValue` skips the focused field.

## Melody Transcriber
**Recording taps one program, never a device.** `NO_FALLBACK` in `capture.py` is essential: without
it the sound server silently moves the recording to the default input, usually the microphone, when
the stream ends (seen on PipeWire 1.0). When a stream ends, `Recorder` looks for a new one of the
same program. `same_origin` refuses requests from other websites, which could otherwise record.

**Analysis is a separate process** per job: it keeps the server responsive, can be killed, and frees
graphics memory. It reports with `@step` and `@error` lines. Separation (BS-RoFormer), then the
loudness of the vocals decides between sung and instrumental; RMVPE for singing, `extract.py` for
instruments, Beat This! for beats. Any failure of the networks falls back to `extract.py` with a
warning. `TUNELAB_NO_GPU=1` forces that; `TUNELAB_MODELS` moves the weights (`~/.cache/tunelab`;
Beat This! uses `~/.cache/torch`).

**Two versions of each candidate:** `notes` in seconds as performed, and `melody`, the snapped
document that is saved. Snapping goes through `notation.Tune`, so it is quarters or thirds of a beat.

**Guiding by hand.** An analysis leaves its separated audio, beats and paths in a work folder
(`info.json`); `guide.py` reads that, so a guided guess needs no new separation. Highlights are one
grid of cells (`guide.GRID`), sent as runs; the same cells are drawn and searched. `Marks.allowed`
says where notes may be: at times with a highlight only inside it, at other times as in the
automatic search, or nowhere ("only"). It masks the salience (`extract.notes_from_salience`) or the
network's output (`models.sung_pitch`). With nothing highlighted the result must equal the
automatic one; a test checks that. `dim_overtones` changes only the picture, never the search.
The page keeps highlights in `sessionStorage`, per recording.

## Files on disk
`library/` (or `$TUNELAB_LIBRARY`): `projects/<id>.json`, `melodies/<id>.json`, `favorites.json`,
`settings.json`, `recordings/<id>.wav`, `trash/`. Formats are the models in `documents.py`; unknown fields are rejected
and `version` is 1. Saving sends the revision (content hash) that was opened; a mismatch is
HTTP 409 and the user is asked. The generator's database is `data/tunes.db` (or `$TUNELAB_DB`).

## Tests
| Command | Covers |
|---|---|
| `uv run pytest` | Everything in Python, including the browser tests below |
| `uv run pytest tests/test_e2e.py` | Real mouse and keyboard in Chrome |
| `uv run pytest tests/test_monkey.py` | Random input, checking invariants after each step |
| `npm test` | Pure JS modules (needs `npm install --ignore-scripts` once) |
| `uv run tunelab-check` | Quality of the scorer |

Tests use temporary folders through the environment variables above and never touch user data.
In the page, `window.tunelab` exposes store, roll, player and actions for tests and debugging.
